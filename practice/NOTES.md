## 第 1 课 · 可复现的基线（W1）

### 一句话

让"跑两次结果一样"从**感觉**变成**能自动验证的事实**。

### 1. 随机性有三个源头，但它们共用一条种子流

一个训练脚本里的随机性来自三处：

| 来源 | 代码位置 | 影响 |
|---|---|---|
| 数据生成 | `torch.randn(N, 1)` | 数据集本身 |
| 权重初始化 | `nn.Linear(...)` 的内部初始化 | 模型起点 |
| 数据打乱 | `DataLoader(..., shuffle=True)` | 每轮的 batch 顺序 |

关键理解：**它们不是三个独立的随机源，而是从同一个全局生成器里连续取数**。所以在最前面调用一次 `torch.manual_seed(seed)`，后面所有地方都被钉死了——不需要在每个地方都写一次。

顺序很重要：`manual_seed` 必须放在**任何**随机调用之前。放在造数据之后，前面那步就不受控。

### 2. `torch.manual_seed` 也管 GPU

很多人以为 GPU 上要额外写 `torch.cuda.manual_seed_all()`。不需要——`torch.manual_seed()` 内部会一并设置所有设备的种子。（多卡场景另说。）

### 3. 验收要用 8 位小数，不是 4 位

第一课最容易犯的错：靠眼睛看 4 位小数判断"两次一样"。

- 4 位是给人看的，会被四舍五入掩盖差异
- 8 位是给程序看的，能暴露浮点层面的漂移
- 真正的验收标准是**逐位一致**，不是"看着差不多"

### 4. CONFIG 的边界：什么该进，什么不该进

判断标准只有一条：**你会不会去调它。**

| 该进 CONFIG | 不该进 |
|---|---|
| lr、batch、epochs、hidden_dim | `device`（环境属性，换机器本来就该变） |
| `noise_std`（会想试噪声大点） | `x ∈ [-3, 3]`（数据集固有定义，基本不会调） |
| `data_weight`（会想试信号强弱） | 代码逻辑本身 |

灰色地带靠自己判断，**但判断时要能说出理由**。

### 5. 抽 CONFIG 时最容易漏的地方

**不是主逻辑里的参数，而是验证/展示代码里的同一个数。**

踩过的具体例子：`data_weight` 已经抽进 CONFIG 了，但最后画对照表那行还写着 `+ 0.5 * x`。这是个**真 bug**——改 CONFIG 后，训练数据变了而"真值"没变，你会去调一个根本没问题的地方。

**教训**：抽完之后用搜索功能找一遍那个数字，确认没有漏网的。

### 6. 重构的验收标准：行为不变

改结构（抽 CONFIG、改函数签名、拆分文件）之后，**输出必须逐位相同**。

这次的做法：重构前后各跑一次，对比 `train_loss` / `val_loss` 的 8 位小数。一致 = 重构成功；不一致 = 你改到了逻辑。

这条习惯的价值：以后你改动别人的代码、或者优化自己的训练脚本时，它是唯一能证明"我没搞坏"的手段。

### 7. 遗留问题（下次补）

- [ ] 打印太多会污染日志，以后要换成 `logging` 或写文件
- [ ] `EPOCHS = CONFIG['epochs']` 这层中间变量要不要留？还没想清楚
- [ ] 还没试过：改 `noise_std` 会怎么影响最终 val_loss？（这正好是第一次"真调参"）

## 第 2 课 · 过拟合诊断与数据增强（W3）

### 一句话

**准确率高低不是重点，"训练集和测试集的差值"才是模型健康度。**

### 1. 三分类诊断（所有训练问题的第一个岔路口）

| 训练准确率 | 测试准确率 | 差值 | 诊断 | 处方 |
|---|---|---|---|---|
| 低 | 低 | 小 | 欠拟合 | 多训、加宽加深、降 lr |
| 高 | 低 | **大** | 过拟合 | 数据增强、正则、早停 |
| 高 | 高 | 小 | 健康 | —— |

关键是**必须同时有两个数**。只有一个测试准确率，你根本判断不出问题出在哪。

### 2. 过拟合的真正信号：不是 test 下降，而是 train 涨 + test 平

我的实测数据（无增强，20 轮）：

| | epoch 12 | epoch 20 |
|---|---|---|
| train | 87.27% | **95.10%**（+7.8） |
| test | 75.06% | **74.97%**（−0.1） |

测试准确率几乎没动，但训练准确率涨了 7.8 个点——**模型在背答案，不是在学特征**。

如果只盯着 test 看，会误以为"训练已经到头了"；实际上模型还在疯狂过拟合，只是测试集看不出增益。

### 3. 数据增强：制造"同一张图的不同版本"

**原理**：一张猫的图，平移几像素、左右翻一下，它还是猫。把这些变体喂给模型，等于凭空扩充了数据集，逼它学**对这些变换不变的特征**，而不是记像素位置。

**CIFAR-10 常用的两种**：

```python
train_transform = transforms.Compose([
    transforms.RandomCrop(32, padding=4),   # 先补到 40×40，再随机裁回 32×32 → 位置变化
    transforms.RandomHorizontalFlip(),      # 50% 概率左右翻转 → 朝向变化
    transforms.ToTensor(),
])

test_transform = transforms.ToTensor()      # 测试集保持原样
```

**两条铁律**：

1. **只用于训练集**。测试集要随机增强的话，每次评估结果都不一样，没法比较。
2. **几何变换要放在 `ToTensor()` 之前**。RandomCrop / HFlip 作用于 PIL 图像；放到 ToTensor 之后就变成在张量上操作，语义和速度都不一样。

### 4. 认知陷阱：加增强后训练准确率会掉，这是好事

| | 无增强 | +增强 |
|---|---|---|
| train | 95.10% | **79.50%**（掉了 15.6） |
| test | 74.97% | **78.81%**（涨了 3.84） |
| gap | 20.1 | **0.7** |

训练任务被故意变难了，所以训练准确率下降是**预期行为**。判断进步只能看 `test`。

### 5. 下一步该继续训练还是改模型？

看 **test 曲线**：

- **还在涨** → 继续训练（我的实验 #5，ep20 还在上升，说明没收敛）
- **平台了，但 train 还在涨** → 改正则/增强/早停
- **两个都不动** → 加模型容量

所以"训练多少轮"不该拍脑袋，看曲线决定。

### 6. 这一课踩到的两个工程坑

**a. 抽函数参数后，函数体里的旧名字没改**

```python
def evaluate(loader):
    for xb, yb in test_loader:   # ← 参数加了，循环没改
```

这个 bug 不报错，只会让 `evaluate(train_loader)` 悄悄在测试集上评估，然后把结果当训练准确率打印。**两个数字会一模一样，还以为是好事。**

教训：给函数加参数后，回头搜一遍函数体里所有旧名字。

**b. Windows 上 `num_workers > 0` 必须配 `__main__` 保护**

否则子进程会重新执行整个脚本，脚本又开始建 DataLoader、又开子进程……无限递归直到卡死。

```python
def main():
    ...

if __name__ == "__main__":
    main()
```

### 7. 遗留问题（下次补）

- [ ] 加增强后训练变慢：`num_workers=0` 让预处理和 GPU 串行，GPU 在等 CPU
- [ ] `transforms.ToTensor()` 只做了 /255，还没试过 `Normalize`（用 CIFAR 的均值方差）
- [ ] 还没试：weight decay、cosine 学习率调度、早停
- [ ] 训练集准确率还是偏低（79.5%），模型容量可能不够——下一步可以加到 4 层卷积

## 第 3 课 · BatchNorm 与学习率调度（W4）

### 一句话

**BN 解决收敛速度，调度解决震荡。只加 BN 不加调度，收益会被震荡吃掉。**

### 1. BN 加在哪、参数写多少

```python
nn.Conv2d(3, 32, 3, padding=1),
nn.BatchNorm2d(32),      # ← 32 必须等于前一个 Conv 的 out_channels
nn.ReLU(),
```

**顺序不能换**：`Conv → BN → ReLU`。

因为 ReLU 会把所有负数砍成 0，如果特征本身整体偏负，ReLU 之后一大片全是 0，BN 再标准化也救不回来。先 BN 把分布拉到以 0 为中心，ReLU 才能正常激活一半。

**参数写错的报错**：`running_mean should contain 32 elements not 3`——这里的数字是**通道数**，不是图片尺寸、不是类别数。

### 2. BN 有"训练时"和"推理时"两套行为

| 阶段 | 用谁的均值方差 |
|---|---|
| `model.train()` | 当前 batch 的，同时**累计**一份全局 running stats |
| `model.eval()` | 用累计好的那份，不看当前 batch |

所以 `model.train()` / `model.eval()` 从"少一点点"变成了"必须写对"。忘了 `eval()`，评估结果会随 batch 组成跳动。

### 3. 实测：BN 单独用是"快但抖"

40 轮、同样 lr=1e-3、同样数据增强，只差有没有 BN：

| 区间 | 无 BN | 加 BN |
|---|---|---|
| 1–10 均值 | 64.97 | **70.32**（+5.35） |
| 31–40 均值 | 80.77 | 81.15（+0.38） |
| 峰值 | 81.33 | **83.29**（+1.96） |
| 末 10 轮 std | 0.48 | **1.99**（×4） |

**结论**：BN 让前期收敛快很多，峰值也抬高了 2 个点，但**末段平均只涨 0.38——中间 1.6 个点被震荡吃掉了**。

### 4. 怎么区分"过拟合"和"优化震荡"（关键判据）

| 现象 | train | test | 诊断 |
|---|---|---|---|
| train 涨、test 跌 | ↑ | ↓ | **过拟合**，gap 扩大 |
| **train 和 test 同步跌** | ↓ | ↓ | **优化震荡**，权重在曲面上来回弹 |

实测数据：

```
ep23 → 79.84      ep24 → 70.14      train 也同步掉到 71.70
ep35 → 82.01      ep36 → 77.11      train 也同步掉到 79.06
```

两个一起掉，就不是模型"学过头了"，而是**优化器在乱跳**。

**为什么会这样**：BN 改变了损失曲面的尺度，等效于把学习率放大了。BN 论文里"可以用更大 lr"的前提是**配合调度**，不是无脑用。

### 5. 余弦退火：把 lr 慢慢降到 0

```python
scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(
    optimizer, T_max=CONFIG["epochs"]
)

for epoch in range(1, EPOCHS + 1):
    ...训练...
    ...评估...
    scheduler.step()          # ← 每个 epoch 末尾调一次
```

**位置很关键**：`scheduler.step()` 在 **epoch 层**调用（每轮一次），不要放进 batch 循环（那是 `OneCycleLR` 之类的用法）。

原理：前期保持大 lr 快速下降，后期 lr → 0，模型"慢慢落进"谷底而不是在谷底来回蹦。

**验证是否生效**：把 lr 打印出来，40 轮里应该从 `0.001000` 平滑衰减到 `0.000000`。

### 6. 阶段 3 完整成绩单（四个改进，同数据同模型）

```
74.97%  基线（无增强无正则）
78.81%  + 数据增强         (+3.84)
81.15%  + BatchNorm        (+2.34)
84.34%  + 余弦学习率调度    (+3.19)
                          ────────
                          +9.37 点
```

四个改动没有一个是"调参玄学"，每一个都有明确的机制解释。

### 7. 遗留问题

- [ ] 84.34% 之后，末 10 轮标准差 0.41，已经收敛——下一个瓶颈大概率是**模型容量**，该换结构了
- [ ] 没试过：`Normalize`（用 CIFAR 均值方差）、weight decay、label smoothing
- [ ] `Dropout(0.3)` 一直包含在基线里，从没单独消融过，不知道它到底贡献了多少

## 第 4 课 · 残差连接与论文精读（W7）

### 一句话

残差连接改造的是**优化难度**，不是表达能力——它让"好解"变得"可达"。

### 1. 退化问题 ≠ 过拟合

| | 训练误差 | 测试误差 | 原因 |
|---|---|---|---|
| 过拟合 | 很低 | 高 | 记答案 |
| **退化** | **也很高** | 高 | **优化器训不动** |

**判据**：看到"训练误差更高"，就同时否掉了过拟合和容量不足两个解释。

### 2. 论文的核心论证（值得背下来）

```
① 深层网络如果多出来的层全学成恒等映射 → 训练误差至少该和浅层一样好
② 但实测更深反而更差
③ 所以：好解是存在的，只是优化器走不到
④ 定位病因 = 优化问题，不是表达问题
```

第 ① 步是整个论证的地基。**"至少不该更差"这个下界，把问题从"能力不足"逼成了"优化困难"。**

### 3. 解法：把"学恒等"变成"学零"

```
原来的层：  y = F(x)          要恒等 → F 得学成"x"（难）
残差块：    y = F(x) + x      要恒等 → F ≈ 0 就行（容易）
```

### 4. BasicBlock 的四个设计决定

| 写法 | 原因 |
|---|---|
| `padding=1` + `kernel=3` | 卷积后尺寸不变，是能相加的前提 |
| `bias=False` | 后面接 BN，bias 会被减均值吃掉，纯属浪费 |
| `out + x` 在**第二个 BN 之后、ReLU 之前** | 先加再激活；先激活再加可能得到负数，残差意义被削弱 |
| 每个 stage 只有**第一个块**带 stride 和 1×1 投影 | 变形只在入口做一次，stage 内部保持同构 |

### 5. shortcut 的两种形式（论文 Table 3）

| 方案 | 形状变化时 | 参数量 | ResNet-34 top-1 |
|---|---|---|---|
| A 零填充 | 补零到目标通道 | 0 | 25.03 |
| B **1×1 投影** | 1×1 卷积映射 | 有 | **24.52** |
| C 全投影 | 所有 shortcut 都用 1×1 | 最多 | 略好，未采用 |

**A 和 B 只差 0.51 个点** → 论文结论："projection shortcuts are **not essential**"。

**真正起作用的是"有捷径"，不是"捷径怎么对齐形状"。**

⚠️ 注意：形状一变，"纯恒等"物理上就不存在了（64 通道加不到 128 通道上）。所以 A 是"零填充 + 恒等"，不是纯恒等。

### 6. ⚠️ 最重要的辨析：梯度高速路不是原文的解释

我之前讲"残差给梯度修了高速路，解决梯度消失"——**这是业界流行说法，论文明确排除了它**。

论文 Section 4.1 原文：

> "this optimization difficulty is **unlikely** to be caused by vanishing gradients. These plain networks are trained with BN... **So neither forward nor backward signals vanish.**"

论文自己的猜想是 **"exponentially low convergence rates"**（收敛速度指数级变慢），并承认原因待研究。

| 解释 | 来源 | 和原文一致吗 |
|---|---|---|
| 恒等映射容易学（学零） | Section 3.1 | ✅ 论文核心论证 |
| 梯度高速路 | 业界流行 | ❌ 论文明确排除 |
| 2ⁿ 条路径的隐式集成 | Veit et al. 2016 | 📖 后续工作 |

**教训：一手论文永远优先于二手转述——包括我给你讲的。**

### 7. 读论文的七步论证链（通用模板）

| 步骤 | ResNet 里对应 |
|---|---|
| ① 观察现象 | Figure 1：56 层训练误差 > 20 层 |
| ② 排除其他解释 | 训练误差更高 → 不是过拟合；层更多 → 不是容量不足 |
| ③ 理论推导 | 深层网络至少该和浅层一样好 |
| ④ 定位病因 | 恒等映射难学 → 优化问题 |
| ⑤ 提出方法 | `y = F(x) + x` |
| ⑥ 验证方法 | Table 2：34 层 ResNet vs plain-34，降 3.5 点 |
| ⑦ 消融实验 | Table 3：三种 shortcut 对比 |

**任何论文都可以先找这七步。缺哪步，就是它最容易被攻击的地方。**

三个阅读警惕点：
1. **摘要里的数字要看清条件**（ResNet 的 3.57% 是 ensemble，不是单模型）
2. **消融实验比主结果重要**（主结果告诉你"它能行"，消融告诉你"为什么能行"）
3. **作者的解释和流行的解释可能不一致**（见第 6 点）

### 8. 一个反直觉的发现

论文 Table 2：**18 层时 plain 和 ResNet 几乎一样**（27.94 vs 27.88）。

原因：网络"不够深"时普通网络照样能训好，**残差只在深到训不动时才显出价值**。

→ 这解释了我在 SmallCNN（3 层卷积）上的经历：加不加残差无所谓；一旦堆到 34 层就是生死差别。

### 9. 实测成绩（ResNet-18 on CIFAR-10）

| 区间 | train | test | gap |
|---|---|---|---|
| 1–10 | 76.08% | 74.72% | 1.36 |
| 21–30 | 98.12% | 91.31% | 6.81 |
| 31–40 | 99.75% | **92.47%** | **7.28** |

- 比 SmallCNN 的 84.34% **高 8.13 点**
- 但 gap 从 2.6 涨到 7.28 → **容量够了，开始过拟合**
- 每轮 34s，40 轮共 23.4 分钟

### 10. 遗留问题

- [ ] `Adam(weight_decay=...)` 实现的是 **L2 正则**（加进梯度），不是真正的权重衰减；应该用 `AdamW`。下次验证差多少。
- [ ] 论文 Section 4.2 的 CIFAR-10 表（20/32/44/56/110 层）还没读——**那张表和我自己的实验直接对应**
- [ ] 为什么 1000 层的 ResNet 反而变差？
- [ ] 还没写 Bottleneck（50/101/152 层用）

## 第 5 课 · 正则化的量级与"对症"（W8）

### 一句话

**两个独立的判断：① 这个手段生效了吗？② 这个手段治得了我的病吗？** 我这次只验证了 ①。

### 1. weight_decay 的数值本身没有意义

AdamW 每步做两件独立的事：

```
梯度更新：  w ← w − lr · m/√v        量级 ≈ lr
权重衰减：  w ← w · (1 − lr·λ)        量级 ≈ lr·λ·|w|
```

`m/√v` 被归一化到约 ±1，所以：

**有效强度 = λ · |w|**（衰减相对梯度的比例）

### 2. 总效果看累积

```
w_n ≈ w_0 · e^{−n·lr·λ}
```

**决定性的是 `n · lr · λ` 这个乘积**，不是 λ 单独。

我的配置：`n = 391 × 40 = 15,640 步，lr = 1e-3`

| λ | n·lr·λ | 累计衰减 |
|---|---|---|
| 1e-4 | 0.0016 | 0.16% |
| 5e-4 | 0.0078 | 0.78% |
| 1e-3 | 0.0156 | 1.55% |
| **1e-2** | **0.078（含余弦折半）** | **7.7%** |
| 5e-2 | 0.39 | 32% |

### 3. ⚠️ 余弦调度会让 weight decay 打折

这是我自己算错的地方：以为 `lr = 1e-3` 恒定，算出 14.5%。

**实际上余弦退火让平均 lr 只有峰值的 51%**，所以 `Σ(lr × steps) = 8.02` 而不是 15.64，真实衰减 **7.7%**。

**教训**：讲"累积量"时不能拿初始 lr 去乘步数，要算 lr 的实际积分。

### 4. 为什么 1e-4 和 1e-2 都没效果

两次实验的结果（末 10 轮均值）：

| 配置 | train | test | gap |
|---|---|---|---|
| Adam, wd=0 | 99.75% | 92.47% | 7.28 |
| AdamW, wd=1e-4 | 99.77% | 92.59% | 7.18 |
| AdamW, wd=1e-2 | 99.74% | 92.49% | 7.25 |

**三组几乎完全一样。** 7.7% 的权重收缩，没能让 train 准确率动一个千分位。

三个原因：

1. **深度网络的记忆不靠"大权重"**——是靠大量小权重分布式编码，L2 范数惩罚压不住
2. **14% / 7.7% 的收缩面对 11M 参数的容量还是太弱**（5 万张图 vs 1117 万参数，每个参数只对应 0.004 张图）
3. **gap 7 点对 CIFAR-10 + ResNet-18 是正常值**，不是病态过拟合，没什么"需要治"的

### 5. 最硬的对照证据

| 手段 | 效果 |
|---|---|
| RandomCrop + HFlip | **+3.84 点** |
| weight decay（0 → 1e-2） | **+0.02 点** |

差 200 倍。**病根是"数据不够"，对症的药就是"让数据看起来更多"（数据增强）**，而不是"限制权重"。

### 6. 可以迁移到所有超参的规则

**① 正则化的强度是相对量**
任何正则项（L2、Dropout、Label Smoothing）都要问"它和主梯度相比多大"，而不是"这个数字大不大"。

**② 超参量级依赖优化器**

| 优化器 | wd 常用范围 |
|---|---|
| SGD | 1e-4 ~ 5e-4 |
| Adam | 1e-4 ~ 1e-3 |
| **AdamW** | **1e-2 ~ 5e-2** |

**③ 抄别人的超参时，先算它的"累积量"，再判断是否可比**

### 7. 最大的收获：机制发生 ≠ 机制对症

我算出了"权重确实被缩小了 7.7%"，这是真的（用零梯度的 AdamW 验证过）。但我把它当成了"过拟合会好转"的证据——**这两个是独立命题**。

**"我做了 A"不等于"A 解决了 B"。** 做实验最容易犯的错就是这个。

正确的流程应该是：

```
① 结果不符预期 → 先查代码有没有 bug（排除实现错误）
② 验证机制真的执行了（确认 A 发生了）
③ 才判断 A 是否对症（这时才轮到质疑假设）
```

### 8. 遗留问题

- [ ] 换成 `RandomErasing`（一行 transform）再试，验证"数据增强 > 权重惩罚"这个判断
- [ ] 余弦调度 + weight decay 的组合会互相削弱，如果要用强 wd，得配合恒定 lr
- [ ] 如果数据增强也不行，下一个方向是 label smoothing 或 CutMix/MixUp

## 附录 · 慢下载怎么破

这条是通用技能，以后下数据集、下预训练权重都会用到。

**症状**：单线程下载只有 10–40 KB/s，170 MB 要几个小时。

**诊断顺序**：

1. **先看单连接速度上限**。很多学术站点（如 `cs.toronto.edu`）单条 TCP 连接被限速在 40 KB/s 左右，但**整体带宽不差**。
2. **确认服务器支持分段**：请求头里看 `Accept-Ranges: bytes`。
3. **开多线程分段下载**，每块用 `Range` 请求独立下载。
4. **并发数从 8 开始，别一上来就 16**。实测 16 线程全部卡死（0 进展），8 线程反而跑到 0.21 MB/s，5 倍于单线程。

**实测对比**（CIFAR-10，170 MB）：

| 方式 | 速度 | 结果 |
|---|---|---|
| 直连单线程 | 10 KB/s | 4–5 小时，放弃 |
| 代理 + 单线程 | 40 KB/s | 70 分钟 |
| 代理 + 16 线程 | — | **全部卡死** |
| 代理 + 8 线程分块 | 0.21 MB/s | **13 分钟完成** |

**另一条经验**：`TUN 模式 ≠ 全网走节点`。TUN 只负责把流量截给代理软件，走直连还是走节点仍由**分流规则**决定——所以开了 TUN 也可能对某些站点走直连。

**最后**：下完一定要验 MD5。断点续传、多线程拼接都可能出问题，校验和是唯一可信的证据。
